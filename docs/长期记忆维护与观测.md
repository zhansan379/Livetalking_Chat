# 长期记忆维护与观测

> 面向后续开发的内部文档：中长期记忆（extract / recall / consolidate 三管线）如何运作、此前的"整理空转循环"及其两层根因、收敛防线、以及 OBS 观测面板的数据链路。
> 适用代码：`agent/longterm.py`、`agent/config.py`、`capabilities/interview/tools.py`、`obs/query.py`、`obs/routes.py`、`web/obs.html`。
> 关联：[[persona_capability_设计]]、[[OBS完整LLM输入输出与提示词测试]]。

---

## 1. 概览

长期记忆是三个异步管线协同的结果，全部落在 `data/memory/*.md`（每个文件一条，YAML frontmatter 含 `name/description/type/created_at/updated_at`），并由 `data/memory/_INDEX.md` 建索引供检索。

| 管线 | 触发 | 作用 |
|------|------|------|
| **提取 extract** | 每 `extract_every_n` 轮对话 | 把一段对话里值得记住的 user 画像提炼为候选，落盘为记忆文件 |
| **召回 recall** | 每次回复前 | 按相关性把若干记忆注入上下文（检索 + 过滤，本次未改） |
| **整理 consolidate** | 记忆条数 ≥ `consolidate_threshold` | 后台把整库喂 LLM 去重/合并，写回后条数应降下来 |

---

## 2. 核心缺陷：consolidate"整理空转循环"

### 现象（运行时证据）
`data/memory/` 涨到 26 条降不下来。OBS trace 显示 `longterm_consolidate` 反复触发，每次耗时 ~50s、输入约 1200 token / 输出约 3000+ token——**LLM 在逐条扩写而不是合并**，且不论输出多少条都写不回去，导致条数 ≥ 阈值、派生下一轮整理，形成僵尸空转。

### 根因（两层，均已在本次修掉）

1. **LLM 对"去重整理"的提示词不服从** —— 默认行为是逐条扩写、卷走条数，而非合并压缩。
   修复：提示词强约束 + 硬封顶 `consolidate_keep`，见 §3-A。

2. **`_call_consolidate` 的 slug 过滤 bug（真正的元凶）**
   `agent/longterm.py` 中 `_candidate_to_record()` 原先**从不给记录设 `slug`**，而 `_call_consolidate` 的落盘过滤条件是 `rec.type in MEMORY_TYPES and rec.name and rec.body and rec.slug`——于是 LLM 合并出的每条记忆都因 `rec.slug` 为空被丢弃，`out` 恒为 `[]`。consolidate 外部见到 `not cleaned: return` 直接跳过写库，**任何整理都实际不生效**。
   修复：`_candidate_to_record` 里补 `rec.slug = _slugify(rec.name)`。存量 25 条立即收敛到 6 条。

> ⚠️ 排查线索备忘：若再现"整理 trace 显示 `after: 0` 但文件没减少"，先看 `_call_consolidate` 的落盘过滤是否丢掉了全部候选（slug/字段缺失），再看 LLM 返回是否被 `_extract_json_array` 正确解析。

## 3. 收敛防线设计

目标：整理写回后条数**必须 < threshold**，把"整理完又触发"的空转彻底终结；同时避免阈值震荡导致频繁整理。

### A. 合并硬封顶（`agent/longterm.py::_call_consolidate`）
- 新增配置 `longterm_consolidate_keep`（默认 8，须 < threshold=10）。
- 提示词强制："合并后总条数必须严格 ≤ N；相近多条并成一条；过时/一次性/环境观察直接删；每条 body 精炼一句话；宁可丢细节，总量必须 ≤ N。"
- 代码兜底：LLM 结果 `out = out[:max(1, keep)]`——即使它照抄 25 条，也截到 8 条。
- 长期记忆是压缩画像，宁丢旧细节。

### B. 统一触发 + 冷却 + 防重入（`agent/longterm.py`）
- 模块级守卫：
  ```python
  _consolidating        # 整理进行中：防重入，也防 consolidate 内部写回触发自己
  _consolidate_pending  # 已有一发调度的待执行标志
  _last_consolidate_done # 上次整理结束的 monotonic 时刻，作冷却基准
  ```
- `write_memory()` 末尾统一调 `_schedule_consolidation_if_needed()`——任何写路径（extract / interview / 其它能力）经此落盘都会走 consolidated，不再只 extract 一条路径。
- 调度是事件循环感知的：有 running loop 用 `asyncio.create_task`，否则守护线程 `asyncio.run`。
- `consolidate_memories()` 入口置 `_consolidating=True`、`finally` 里复位并推进 `_last_consolidate_done`（冷却 `longterm_consolidate_cooldown`，默认 300s）。内部写回再触发时因 `_consolidating` 直接 return。

### C. extract 过滤增强（`_call_extract` 提示词）
当前环境/设备/一次性观察（摄像头画面、此刻几点、当下瞬时心情）不得提取为 user 画像。

## 4. 配置项（`agent/config.py` + `agent/agent_config.yaml`）

| 配置 | 默认 | 说明 |
|------|------|------|
| `longterm.consolidate_threshold` | 10 | 达到该条数触发整理 |
| `longterm.consolidate_keep` | 8 | 整理后条数硬上限（须 < threshold），保证收敛 |
| `longterm.consolidate_cooldown` | 300 | 两次整理最小间隔（秒），防阈值震荡 |

配置文件缺省即生效；新增即用，无需迁移。

## 5. interview 覆盖式 + 历史归档（`capabilities/interview/tools.py::_maybe_remember`）

- **覆盖式**：删掉原先的时间戳 slug（那会让每次面试都新建一条、无限堆积）。改回固定 name→slug → `write_memory` 同名覆盖 → 同一岗位只留最新一条复盘。
- **能力层历史**：全量 report 另存 `data/capabilities/interview/history/{role}-{level}-{YYYYMMDDHHMM}.json`（`state.py` 原子写，异常静默），长期库之外留存完整过程。

## 6. OBS 观测：记忆维护面板

让"提取/整理的细节"可观测，供 `web/obs.html` 的「长期记忆维护」面板展示。

### 事件
- `extract_longterm_memory`：`new_trace(kind="longterm_extract")` 内发 `type="memory_extract"`，记 `candidates`(LLM 候选数) / `written`(实际落盘) / `skipped`。
- `consolidate_memories`：`new_trace(kind="longterm_consolidate")` 内发 `type="memory_consolidate"`，记 `before` / `after`。
- 均用 `obs.emit`，失败静默不炸主流程；同 trace_id。

### 聚合端（`obs/query.py::memory_maintenance`）
按 kind ∈ `("longterm_extract", "longterm_consolidate")` 聚成逐条记录，按 ts 倒序：
- root：ts / session_id / kind / success / elapsed_ms / llm_calls
- LLM：model / route / tokens / llm_ms、成功态
- 业务量：提取→ candidates/written/skipped；整理→ before/after
- `llm_out`：**取 `llm_call.output`**（该字段才是助手返回文本；`messages` 只含输入 system/user），长度封顶 4000，供前端展开预览
- `stats.extract`（次数/成功率/均耗时/均 token/累计 written）、`stats.consolidate`（次数/均耗时/`last_before→last_after`，`co[0]` 依赖倒序 = 最近一次）

### 端点与面板
- `obs/routes.py`：`/api/obs/memory` → `obs_memory`（调 `memory_maintenance`）。
- `web/obs.html`「长期记忆维护」区块：
  - 指标卡行 `#memCards`（提取次数/成功率/均耗时、整理次数/均耗时/最近 前→后——最近整理显示"已收敛"色标）
  - 记录表 `#memTable/#memBody/#memCount`（提取↔整理 badge、会话、量、模型、耗时 总/LLM、Tokens、状态）
  - 行点击展开 `memExpanded[trace_id]` → 显示该次 `llm_out`（经 `esc` 的内联代码块）
  - `refreshAll()` 并行 `fetch('/api/obs/memory?window=86400')`，主题/调色板复用现有 `PAL` 与 badge 色。

## 7. 存量收敛 & 验证清单

```bash
# 手动收敛一次（改完 consolidate 之后对既有库跑一遍）
python -X utf8 -c "import asyncio; from agent.longterm import consolidate_memories; asyncio.run(consolidate_memories('manual-cleanup'))"
ls data/memory/*.md | grep -v _INDEX | wc -l   # 期望 < threshold（当前 6）
```

验证要点：
1. **收敛**：consolidate trace 出现 `memory_consolidate`，`after < before`；再次运行因 `6 < threshold` 立即短路，`events.jsonl` 不再新增 `longterm_merge`（对照修复前每轮烧一次）。
2. **slug bug 不复现**：`after: 0` 且文件数不变 即意味着落盘过滤又丢光了候选——回查 §2 根因 2。
3. **interview 覆盖**：跑一次面试结束 → 长期记忆固定 slug 只更新不新增，`history/` 出现时间戳归档。
4. **观测面板**：`memory_maintenance` 返回含 `llm_out`/`before→after` 的记录；obs.html 新面板指标 + 记录 + 可展开清单、暗色切换正常。

> ⚠️ 环境留意：开发机出网受限，仅清华 pip + ModelScope 可达（见 [[dev-machine-network-reachability]]）；consolidate 走 bailian（dashscope，可达）而非 siliconflow。`python -c` 裸进程孤立跑 consolidate 时，`llm_call` 事件可能因未走完整 obs_hook 接线而不落在 trace 内（`model/tok/llm_out` 为空），属测试环境局限，生产经 `new_trace` + `emit_obs` 正常捕获（参考既有 16:47 / 14:47 trace）。
